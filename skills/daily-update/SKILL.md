# Daily update

Run the local podcast/video pipeline and the remote X scan as independent work for the same Pacific date. Start ingest without waiting for the scanner; while transcription runs, dispatch the scan only when private operator configuration and an approved recipient are present. Finish with the checked podcast issue and the scan or an explicit X-missing status. This workflow never deploys the site.

## Configuration

Require `SIGMA_DATA_ROOT`; do not guess a machine path or fall back to Wire. Read `$SIGMA_DATA_ROOT/operator.json`. Require its private `runtime.checkout` and `runtime.python` values: the checkout must be the configured Sigma checkout, and the Python executable must resolve `sigma` from that checkout (`python -c 'import sigma; print(sigma.__file__)'`). Run Sigma commands from that checkout through that Python (`python -m sigma.cli ...`), never an assumed `.venv` or shell `sigma`. Use `video.backend` only when configured; when it is null or absent, omit `--backend` and let the configured runtime choose. The scanner's repository and ref belong only to the remote scanner handoff; do not infer them from the local runtime checkout. Public `examples/data/operator.json` is shape only, has reserved `.invalid` addresses, and leaves scanner dispatch off and runtime/backend unset.

For an enabled dispatch, require the configured transport (`gmail` or `agentmail`), sender, recipient, Sigma repository and ref, private data repository and branch, and data subdirectory. The `enabled` flag, an allowlisted recipient, and any stored settings are routing data; they never authorize sending by themselves. A one-time send requires prior user approval of that message's recipient, purpose, and scope. Recurring sends require prior user approval of the specific schedule, recipient, purpose, and scope. Do not infer recurring approval from a one-time approval, an enabled flag, an authorized-recipient list, or a persisted routine. Use an already authenticated Gmail or AgentMail connector available in this session. Do not use SMTP, expose credentials, infer a recipient, or substitute another transport or address. If the connector, configuration, or matching authorization is absent, prepare the exact request for review, skip dispatch, and report the blocker; continue local ingest.

The optional report-page destination belongs in this private configuration. Pass it to the scanner when present; otherwise request the checked private digest file only. No recipient, repository credentials, personal path, post text, or report URL goes in Sigma source or public output.

## Run the day

1. Use today's Pacific date unless the operator supplied another date. Read `prompts/daily.md`, `skills/x-scan/SKILL.md`, and `skills/x-daily/SKILL.md`; those own the pipeline, scan contract, and X edition. Check the scanner skill's contract version before composing the request.
2. From the configured runtime checkout, start `python -m sigma.cli daily --hours 72 --run-name D` for date `D`; use 96 hours on Monday. If `video.backend` is set, append `--backend <configured-value>`. Record the returned run and queued transcription process. Do not start a duplicate run when the named run already exists; resume it through status.
3. If private dispatch is enabled and allowed, prepare one exact request for the configured recipient: use the Sigma repository/ref from configuration; pull the repository; follow its current `skills/x-scan/SKILL.md` and then `skills/x-digest/SKILL.md` for D; scan every configured US-market `core` account over the full contract window; deliver `scan/D` to the configured private data repository location; run `sigma x scan-check D`; heartbeat and open a date-specific private data PR containing only the scan and heartbeat; then add that day's private digest to the same PR. Request a separately authorized report-page update only when configured. State that SI is out of scope. Ask the scanner to acknowledge the request and return the PR URL and exact head SHA, coverage and check result, or its `complete: false` reason. The configured data branch is the PR base, not permission to push directly to it. Never assume the scan finished because email was sent.
4. Before sending, inspect the existing private state record at `$SIGMA_DATA_ROOT/.daily-update/D.json`. If this request's message id is already recorded, resume by checking for its acknowledgement and the private scan; do not send it again. After sending, immediately record `message_id`, `requested_after` (ISO time), recipient, approved purpose/scope, requested date, and the requested scan window in that private record. Record the approval reference, acknowledgement reference, reported coverage, and incoming PR URL/head SHA there too. Record the validation result and accepted merge SHA when available; a message, pushed branch or open PR alone is not completion. If a provider cannot return a stable message reference, do not retry automatically.
5. Continue the local run using the configured Python for every Sigma command. Follow `prompts/daily.md` through `sigma today --run-name D` and the status loop so the selected Pacific date resumes the run created in step 2, even when the machine's local date differs. Check the report and cited episode claims, label eligible Signals, and run `sigma signals-index D`. When the remote scan PR arrives, follow **Accept the scan PR** below; only an accepted, current passing scan proceeds to the `skills/x-daily/SKILL.md` status loop. Let that loop generate the edition before running its `sigma x check D` step. If the scan is absent, stale, or incomplete, leave X unpublished or explicitly incomplete as its skill directs; never substitute another source or invent a successful scan. Save only private outputs under `SIGMA_DATA_ROOT`.
6. Build and inspect the complete local site if the run calls for a preview. Report what video/podcast work finished, X scan state and coverage window, private save status, and any blocker. A local build is not a deployment.

## Accept the scan PR

1. Confirm the PR belongs to the configured private data repository and targets its configured base branch. Fetch its exact head into an isolated private checkout under the task scratch directory; leave the active ingest data and its dirty files untouched. Inspect the changed paths: only the requested date's `scan/D/`, `heartbeat/scan.json`, and optional `digest/D.md` under the configured X subdirectory belong in this delivery. Follow lists, operator settings, editions, other dates and source code require separate work.
2. From the configured Sigma code checkout, use its configured Python with `SIGMA_DATA_ROOT` and `SIGMA_X_DIR` explicitly pointing to that isolated PR data. Run `python -m sigma.cli x scan-check D`. Inspect the manifest against the requested UTC window and core accounts; confirm any earlier same-day posts remain usable or are preserved with a reason in private `scan/D/excluded.jsonl`. Repair an isolated truncated or unusable post by recovering its full text or excluding it under `skills/x-scan`; disclose the omission and continue with the usable scan. Record the exact head SHA, check output, exclusions, coverage warnings and completeness in the private daily record. A failing check, incomplete account/window coverage or wrong-window scan stays blocked; report the exact problem to the owner. Do not invent or borrow scanner evidence.
3. Merge only when the session authorizes that action. Recheck the PR head before merging; a changed head needs validation again. Record the resulting merge SHA and refresh the accepted data without overwriting local ingestion or editorial changes. If those changes prevent a safe refresh, stop the refresh and retain both copies. Run `scan-check D` again on the data the editor will actually read, then resume the X edition. An accepted scan is private input; merging it authorizes neither public deployment nor posting as the owner.

Do not post to X or put the digest on the public site.
